# SupervisoryChannels

An [OMNeT++](https://omnetpp.org/) simulation of a four-node optical ring network
in which a **supervisory (signalling) channel** circulates a token that lets
nodes reserve **optical data channels**. Client packets arrive through ten
`Source` modules, are queued and aggregated per destination, and are forwarded
around the ring to `Sink` modules.

> **Status: work in progress.** This is an early research snapshot, not a
> runnable example. Several identifiers in `RingNode.cc` are undeclared or
> inconsistent, so the committed source does **not** compile as-is; see
> [Known limitations](#known-limitations).

## What the model does

- `RingTopology` (in the NED file) connects four `RingNode` modules in a
  unidirectional data ring and a counter-rotating supervisory ring. Ten
  `Source` modules feed node 0, and each node has a dedicated `Sink`.
- A token (`tokenType`, defined in `token.msg`) carries the per-channel
  destination table and a count of free channels. A node that receives the
  token marks channels addressed to itself as free, updates the table, and
  forwards the token to its neighbour.
- `Source` generates a `dataType` packet at a uniformly random interval
  (0.1&ndash;0.2&nbsp;s) with a uniformly chosen source/destination node.
- `RingNode` buffers arriving packets, classifies and aggregates them per
  destination into `aggregatedType` messages, and sends packets destined for
  the current node to its sink.
- `Sink` counts received messages and records the total as a scalar.

The aggregation and de-aggregation paths are incomplete; the code contains
commented-out drafts and TODOs rather than a finished protocol implementation.

## Layout

| Path | Purpose |
| --- | --- |
| `SupervisoryChannels.ned` | `RingNode`, `Source` and `Sink` simple modules plus the `RingTopology` network |
| `omnetpp.ini` | Simulation configuration (selects the `RingTopology` network) |
| `RingNode.cc` | Core node behaviour: token handling, buffering, classification, aggregation, forwarding |
| `Source.cc` / `Sink.cc` | Traffic generator and packet sink modules |
| `token.msg` | Message definitions: `tokenType`, `dataType` and `aggregatedType` |
| `parameters.h` | Buffer, channel and timeout constants |
| `Makefile` | Generated by `opp_makemake`; regenerate rather than hand-editing where possible |
| `.oppbuildspec`, `.project`, `.cproject`, `.qtenvrc` | OMNeT++ IDE project/build descriptors and Qtenv playback settings |
| `token_m.{h,cc}` | **Generated** from `token.msg` by the message compiler; not tracked |
| `*.exe` | Prebuilt Windows binaries; build output, not tracked |

## Prerequisites

- OMNeT++ 5.x or 6.x, with `opp_makemake`, `opp_msgc` and
  `opp_configfilepath` on `PATH`
- A C++11/14-capable compiler
- Optional: the OMNeT++ IDE (Eclipse-based) if you prefer the GUI workflow

## Build

From the project directory, with the OMNeT++ environment set up:

```sh
opp_makemake -f --deep -O out -I.   # regenerate the Makefile (optional)
make MODE=release                   # or MODE=debug
```

`make` runs the message compiler to produce `token_m.h` and `token_m.cc` from
`token.msg`, then builds the `supervisoryChannel` executable in the project
root. The model must be completed first (see below) before this succeeds.

## Run

```sh
./supervisoryChannel -u Qtenv     # GUI
./supervisoryChannel -u Cmdenv    # batch / headless
```

Simulation results (`*.sca`, `*.vec`) are written to `results/`, which is
ignored by Git.

## Known limitations

- `RingNode.cc` uses `NUM_LOWBUFFERS` and `NUM_HIGHBUFFERS`, which are not
  defined in `parameters.h`; one loop spells the former `NUM_lOWBUFFERS`.
- `classifing_Aggregation()` calls `getDestinationNode()` on a `dataType`, but
  that message only defines scalar `source` and `destination` fields.
- `deAggregation()` is declared with an `aggregatedType *` argument but called
  without one, and the `aggregatedPkt` member is used as both a queue and a
  pointer.
- The removed `*.exe` files were built on Windows and may not correspond to the
  committed source. No license file is present yet.

These are left for a maintainer to resolve; fixing them requires deciding on
the intended buffer sizes and protocol behaviour, which cannot be verified in
this cleanup.
